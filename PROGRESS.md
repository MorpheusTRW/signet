Generatore puro e deterministico rispetto a un rng iniettabile (`src/ingest/synthetic/`).
- **Filtri** (funzioni pure, `src/filters/`): concentrazione top 10 holder, storico dev wallet, liquidità iniziale, snipe nei primi blocchi, mint/freeze authority. Aggregati in `computeRiskReport` → `RiskReport` (score 0-100, livello low/medium/high, motivi).
- **Sintesi** deterministica da template (`src/signals/summarize.ts`), nessun LLM nel percorso critico.
- **Persistenza SQLite** (better-sqlite3, `src/db/`): tabelle `signals`, `devices`, `paper_trades`. Endpoint `GET /signals`, `GET /signals/:id`, `POST /devices` (genera e restituisce un'API key per device; solo l'hash è salvato).
- **Paper trading** (`src/paper-trading/`): ogni segnale approvabile (rischio non "high") apre una posizione simulata con size limitata dal 20% di esposizione massima del portafoglio (principio 3 di CLAUDE.md), verificato lato server sommando le posizioni ancora aperte. Le posizioni restano "open" per una durata simulata prima di chiudersi e realizzare il PnL, così il limite ha un effetto reale fra segnali concorrenti nel tempo.
- Verificato manualmente end-to-end con `pnpm dev`: eventi sintetici generati, filtrati, sintetizzati, salvati, esposti su `/signals` e `/signals/:id`; `/devices` registra un device con API key in chiaro restituita una sola volta; `paper_trades` popolata con PnL simulato entro il limite di esposizione.

## F3 — Push FCM tier-aware + deep link al segnale

- **Bug pre-esistente corretto**: `services/engine` non caricava mai `.env` (né in F1 né in F2/monetizzazione) — `tsx watch`/`node` non leggono `.env` da soli e non c'era alcun loader. Verificato con un test dal vivo: con l'intervallo sintetico impostato a 1s in `.env`, i segnali continuavano a comparire ogni 8s (il default dello schema), a riprova che il file veniva ignorato. Corretto con il flag nativo di Node `--env-file-if-exists` (disponibile da Node 20.12+, bump di `engines.node` alla radice) negli script `dev`/`start` di `services/engine`, con path relativo `../../.env` perché `pnpm --filter` esegue lo script con cwd = `services/engine/`. Riverificato dal vivo: intervallo, ritardo FREE e intervallo di dispatch delle push ora rispettano davvero i valori in `.env`.
- **firebase-admin** (`src/push/sender.ts`): API modulare corrente (`initializeApp`/`cert` da `firebase-admin/app`, `getMessaging` da `firebase-admin/messaging`), verificata leggendo i `.d.ts` del pacchetto installato. Nota: il campo `token` di `TokenMessage` risulta `@deprecated` in favore di un nuovo targeting per Firebase Installation ID (FID) nella versione più recente — non ancora riflesso nella doc pubblica né nel client `@react-native-firebase/messaging` corrente (che produce ancora solo `token`), quindi si resta su `token` con una nota nel codice da rivedere quando l'ecosistema si sposterà su FID. Senza `FIREBASE_PROJECT_ID`/`FIREBASE_CLIENT_EMAIL`/`FIREBASE_PRIVATE_KEY` il sender degrada a fail-soft (notifiche pianificate ma mai inviate, marcate `failed` con un messaggio chiaro), stesso pattern della verifica HOLDER.
- **Dispatch tier-aware** (`src/push/schedule-signal-push.ts`): per ogni nuovo segnale e ogni device registrato, calcola il tier (`resolveTier`, riusato da F1/monetizzazione) e pianifica: PRO/HOLDER subito; FREE dopo `FREE_SIGNAL_DELAY_SECONDS`, riservando subito la quota giornaliera nello stesso contatore già usato da `GET /signals` (`signal_deliveries` — evita di contare due volte push e feed) e saltando del tutto se la quota è già esaurita. Al FREE che con questo segnale esaurisce la quota viene pianificata anche, una sola volta al giorno (deduplicata via `push_notifications`), la notifica "Limite raggiunto — passa a Pro" con `data.route = "/plans"`.
- **Dispatcher** (`src/push/dispatcher.ts`): sweep periodico (`PUSH_DISPATCH_INTERVAL_MS`, default 5s) disaccoppiato dalle richieste HTTP, invia le notifiche pianificate dovute e segna `sent`/`failed`.

### Passi manuali su Firebase Console (necessari prima di poter testare le push)

1. Su https://console.firebase.google.com crea un progetto (o riusa uno esistente).
2. Aggiungi un'app Android al progetto: package name **esattamente** `com.seekersignal.app` (deve combaciare con `apps/mobile/app.json` → `expo.android.package`). Il certificato SHA-1 di debug è opzionale per il solo FCM (serve per Dynamic Links/Auth, non qui).
3. Scarica `google-services.json` e mettilo in `apps/mobile/google-services.json` (path già referenziato in `app.json`; il file è in `.gitignore`, non va committato).
4. Project Settings (icona ingranaggio) → tab **Service accounts** → "Generate new private key": scarica il JSON dell'account di servizio. Da quel JSON copia in `.env` (alla radice del monorepo):
   - `project_id` → `FIREBASE_PROJECT_ID`
   - `client_email` → `FIREBASE_CLIENT_EMAIL`
   - `private_key` → `FIREBASE_PRIVATE_KEY` (incollalo tra virgolette con gli `\n` letterali così come sono nel JSON)
5. (Consigliato) In Google Cloud Console → IAM, verifica che l'account di servizio abbia solo il ruolo "Firebase Cloud Messaging API Admin" invece di un ruolo ampio come Editor/Owner.
6. Non serve altro per abilitare Cloud Messaging: è attivo automaticamente non appena aggiungi un'app al progetto.
7. Per un test rapido senza passare dal backend: Firebase Console → Cloud Messaging → "Invia messaggio di test" con il token FCM stampato da `useRegisterPushToken` (via log) sul device.
