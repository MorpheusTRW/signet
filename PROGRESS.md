### Passi manuali su Firebase Console (necessari prima di poter testare le push)

1. Su https://console.firebase.google.com crea un progetto (o riusa uno esistente).
2. Aggiungi un'app Android al progetto: package name **esattamente** `com.seekersignal.app` (deve combaciare con `apps/mobile/app.json` → `expo.android.package`). Il certificato SHA-1 di debug è opzionale per il solo FCM (serve per Dynamic Links/Auth, non qui).
3. Scarica `google-services.json` e mettilo in `apps/mobile/google-services.json` (path già referenziato in `app.json`; il file è in `.gitignore`, non va committato).
4. Project Settings (icona ingranaggio) → tab **Service accounts** → "Generate new private key": scarica il JSON dell'account di servizio. Da quel JSON copia in `.env` (alla radice del monorepo):
   - `project_id` → `FIREBASE_PROJECT_ID`
   - `client_email` → `FIREBASE_CLIENT_EMAIL`
   - `private_key` → `FIREBASE_PRIVATE_KEY` (incollalo tra virgolette con gli `\n` letterali così come sono nel JSON)
5. (Consigliato) In Google Cloud Console → IAM, verifica che l'account di servizio abbia solo il ruolo "Firebase Cloud Messaging API Admin" invece di un ruolo ampio come Editor/Owner.
6. Non serve altro per abilitare Cloud Messaging: è attivo automaticamente non appena aggiungi un'app al progetto.
7. Per un test rapido senza passare dal backend: Firebase Console → Cloud Messaging → "Invia messaggio di test" con il token FCM stampato da `useRegisterPushToken` (via log) sul device.

## F4 — `/build-swap` + validateSwapTx condiviso + firma biometrica

- **Ricerca Jupiter Swap API** (developers.jup.ag, verificato 2026-09-24): il flusso classico `/quote`+`/swap` (Metis) è deprecato ("no longer actively maintained, superseded by Swap V2"). Swap V2 ha due percorsi:
  - Meta-Aggregator (`/order`+`/execute`): fee piattaforma **automatica e non configurabile** (a scaglioni per coppia di token) + referral fee opzionale ma con **minimo 50bps** e setup on-chain via referral program — incompatibile con le fee per-tier di CLAUDE.md (HOLDER è 30bps, sotto il minimo).
  - **Router (`GET /swap/v2/build`)**: "Jupiter does not charge swap fees" di suo; `platformFeeBps`+`feeAccount` sono sotto controllo completo dell'integratore (feeAccount può essere un qualsiasi token account, non serve il referral program). Usato questo: è l'unico compatibile con fee arbitrarie per tier.
  - A differenza di `/order`, `/build` non ritorna una tx serializzata ma istruzioni "grezze" da assemblare (`computeBudgetInstructions`, `setupInstructions`, `swapInstruction`, `cleanupInstruction`, `addressesByLookupTableAddress`, `blockhashWithMetadata`): assemblate in `src/swap/build-transaction.ts`.
  - **Verificato dal vivo contro l'API reale** (non solo dalla doc): chiamata a `api.jup.ag/swap/v2/build` per SOL→USDC, confermato che lo schema di risposta, il program Jupiter (`JUP6LkbZbjS1jKKwapdHNy74zcZ3tLUZoi5QNyVTaV4`) e gli altri program coinvolti (System, Associated Token, Token, ComputeBudget) combaciano esattamente con l'implementazione; `buildVersionedTransaction` testato end-to-end contro questa risposta reale con risoluzione di una address lookup table reale via RPC mainnet.
  - **Pump.fun in bonding curve**: confermato che Jupiter **non instrada** i token ancora in bonding curve (pre-migrazione); instrada invece PumpSwap dopo la migrazione ("Jupiter Spot now supports trading of tokens on PumpSwap"). `isJupiterRoutable()` (`src/config/jupiter.ts`) ammette solo `pumpswap`/`meteora-damm`; per `pump-fun`/`meteora-dbc`/`raydium-launchlab` (bonding curve) `/build-swap` risponde 409 proponendo esplicitamente che serve un adapter dedicato, non ancora implementato.
- **`POST /build-swap`**: valida il body, verifica il program del segnale sia instradabile, **controlla il limite del 20% prima di costruire** (riusa `remainingExposureSol` di F1, stesso portafoglio paper), risolve il tier del wallet per la platform fee, chiama Jupiter `/build` con `feeAccount` = ATA wSOL della treasury (`TREASURY_WALLET_PUBKEY`), assembla e serializza la tx. Risposta: tx base64, importo, fee in bps e SOL, quote (con importo di output convertito nei decimali reali del token), `blockhash`/`lastValidBlockHeight` per la conferma post-invio, `tradingMode`. Senza `SOLANA_RPC_URL`/`TREASURY_WALLET_PUBKEY` risponde 503 (fail-soft, stesso pattern di HOLDER/push).
- **`validateSwapTx` condiviso** (`packages/shared/src/validate-swap-tx.ts`, ora dipendenza da `@solana/web3.js`+`@solana/spl-token` anche in shared): verifica fee payer, allowlist dei program (risolvendo le address lookup table), transfer System Program verso destinazioni sconosciute (tramite `SystemInstruction.decodeTransfer`, non un parsing inventato), importo massimo (somma dei transfer verso la wSOL ATA dell'utente). **La platform fee è incassata dentro la swap instruction via CPI**, non come transfer separato: non essendo pubblicamente documentato il layout esatto degli argomenti dell'istruzione Jupiter (evitato decodificarlo a mano per non "inventare" un formato), la fee bps realizzata viene verificata via **simulazione** (`connection.simulateTransaction` + confronto saldo pre/post di `feeAccount`) — l'unico modo corretto e indipendente dalla versione del programma Jupiter. Per questo `validateSwapTx` è async e richiede una `connection` (estensione della firma indicata, necessaria e documentata nel codice).
- **`JUPITER_SWAP_ALLOWED_PROGRAMS`** (`packages/shared/src/jupiter-programs.ts`): allowlist pronta per l'app, costruita solo da costanti ufficiali delle librerie (`SystemProgram.programId`, `ComputeBudgetProgram.programId`, `TOKEN_PROGRAM_ID`, `ASSOCIATED_TOKEN_PROGRAM_ID`), mai stringhe indovinate — confermata contro la risposta reale di Jupiter.
- **Bug corretto**: `loadEnv` non trattava un `KEY=` vuoto in `.env` (convenzione di tutto il progetto per le chiavi opzionali) come "non impostato" — `z.string().default(...)` scatta solo su `undefined`, non su stringa vuota. `JUPITER_API_BASE_URL=` vuoto produceva un base URL vuoto e un errore "Invalid URL" verso Jupiter, scoperto testando dal vivo. Corretto normalizzando `""` → `undefined` prima del parsing zod in `loadEnv`, con test dedicati.
- **App mobile passata a mainnet-beta** (`AppConfig.cluster`): Jupiter instrada solo su mainnet (nessuna liquidità reale su devnet) e i token pump.fun/PumpSwap/Meteora esistono solo lì. Di conseguenza **anche il bottone di debug di F2 ora firma su mainnet** (fee reale trascurabile, ~0.000005 SOL, invece che gratuita su devnet) — cambio deliberato e necessario per F4, segnalato esplicitamente.
